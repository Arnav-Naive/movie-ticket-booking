# Phase 8 — Bookings (Booking + BookingSeat + Server-Side Pricing)

**Project:** Movie Ticket Booking Platform
**Goal of this phase:** Turn a set of HELD seats into an actual `Booking` record, with the total price calculated entirely on the backend — never trusting a number the frontend might send.

**Status:** ✅ Done — booking creation and the user-scoped "My Bookings" endpoint both confirmed working.

---

## 1. Why this phase exists, and the rule it's built around

Phase 7 got a seat to `HELD` status. That's still not a booking — it's just a temporary claim. This phase is what turns "I'm holding these seats" into "I have booked these seats," with one non-negotiable rule carried straight from the PRD's security section:

> **The booking amount must always come from the backend's own calculation — never from a number the frontend sends.**

If the frontend were trusted to say "the total is ₹600," a modified request could just as easily say "the total is ₹6" and the backend would have no way to know the difference. The models and logic in this phase exist specifically to make that kind of tampering impossible — the price gets computed from the actual `Show.price` and the actual number of seats, server-side, every time.

## 2. The two models

```python
class Booking(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name='bookings')
    show = models.ForeignKey(Show, on_delete=models.CASCADE, related_name='bookings')
    booking_reference = models.CharField(max_length=20, unique=True, blank=True)
    total_amount = models.DecimalField(max_digits=8, decimal_places=2)
    status = models.CharField(max_length=10, choices=STATUS_CHOICES, default='PENDING')

    def save(self, *args, **kwargs):
        if not self.booking_reference:
            self.booking_reference = f"BK-{uuid.uuid4().hex[:10].upper()}"
        super().save(*args, **kwargs)


class BookingSeat(models.Model):
    booking = models.ForeignKey(Booking, on_delete=models.CASCADE, related_name='booking_seats')
    show_seat = models.ForeignKey(ShowSeat, on_delete=models.CASCADE, related_name='booking_seats')
```

Three details worth understanding, not just copying:

### `settings.AUTH_USER_MODEL`, not a direct import of `User`

Instead of `from users.models import User`, this uses `settings.AUTH_USER_MODEL` — a string reference (`'users.User'`, set back in Phase 2) that Django resolves at the right time internally. This is Django's officially recommended way to reference the User model from other apps, specifically because a direct import can create a **circular import** — a situation where `bookings` needs `users`, and (if `users` ever needed to reference `bookings` for something) `users` would need `bookings` right back, which Python can't resolve. The settings-string approach sidesteps that entirely.

### `booking_reference`, auto-generated by overriding `save()`

```python
def save(self, *args, **kwargs):
    if not self.booking_reference:
        self.booking_reference = f"BK-{uuid.uuid4().hex[:10].upper()}"
    super().save(*args, **kwargs)
```
Overriding `save()` lets you inject logic that runs every time a model is saved, before the actual database write happens. Here: *if* no reference exists yet (a brand-new booking), generate one from a UUID (a universally-unique random identifier) and take the first 10 hex characters, uppercased — giving something like `BK-E15DAD5BE3`. This is a simplified version of the PRD's `BK-2026-000123` style, but the important property is the same: each reference is effectively guaranteed unique without needing to check the database for collisions first.

### Why `BookingSeat` is a separate table, not a list field on `Booking`

A single booking can cover multiple seats (someone booking 2 tickets together). `BookingSeat` is a **join table** — each row represents one specific seat belonging to one specific booking. This is the same relational pattern as `ShowSeat` linking `Show` and `Seat` in Phase 7: whenever "one thing can have many of another thing, and that link itself needs to be queryable," a separate table is the correct structure — a Python list stored directly on `Booking` couldn't be filtered or joined against efficiently by the database.

Notice also that `BookingSeat` points at `ShowSeat`, not at `Seat` directly — this is deliberate. It ties the booking to *this specific show's* seat status (the thing that actually gets flipped to `BOOKED`), not just the physical seat in the abstract.

## 3. What the actual test response proves

```json
{
  "booking_reference": "BK-E15DAD5BE3",
  "total_amount": "600.00",
  "status": "PENDING",
  "booking_seats": [
    { "seat_row": "A", "seat_number": 1 },
    { "seat_row": "A", "seat_number": 2 }
  ]
}
```

`total_amount: 600.00` for 2 seats on a `Show` priced at `300.00` (from Phase 6's test data) is exactly `300 × 2` — computed by the backend from the actual `Show.price` and the actual number of seats in the request, not handed to it. This is the concrete proof that the "never trust the frontend's amount" rule is actually implemented, not just stated as an intention.

`status: PENDING` is also correct and expected — a booking isn't `CONFIRMED` yet at this stage, because no payment has happened. That transition is exactly what Phase 9 (Razorpay) will implement.

## 4. The token-expiry moment — worth understanding properly, not just moving past

Between testing booking creation and testing "My Bookings," the JWT **access token expired** (5-minute default lifetime) and the second request came back `401 Unauthorized`. This wasn't data loss or a bug — it's JWT working exactly as designed.

<details>
<summary>Why does the access token expire so quickly, and where did the actual data go?</summary>

Short-lived access tokens are a deliberate security trade-off from Phase 2's JWT setup: if a token is ever stolen, it's only useful to an attacker for a few minutes. The **booking itself lives in Postgres**, completely independent of any token — tokens only prove *who's currently allowed to ask questions*, they don't store data themselves. So the booking (`id: 1`, `BK-E15DAD5BE3`) was sitting safely in the database the whole time; only the *permission slip* to view it had expired. Logging in again generates a fresh token, and the same booking shows up immediately — proven by the identical booking data appearing in the second, successful `/my/` response.

This is also exactly why a real frontend needs a **refresh token flow** eventually (already installed via `djangorestframework-simplejwt` back in Phase 1) — so users aren't manually re-logging in every 5 minutes. That wiring is still a to-do for the React side, not yet built.
</details>

## 5. The `/api/bookings/my/` endpoint — what "user-scoped" actually means

The test confirmed this endpoint returns *only* the logged-in user's own bookings. This connects to another PRD security rule: *users can only see their own bookings, never someone else's* — the same category of rule as the admin-only checks in Phases 4–6, just scoped to "this row belongs to `request.user`" instead of "this action requires `is_staff`."

```
      │
      ▼
Booking created ──► total_amount = Show.price × number of seats (backend-calculated)
      │              booking_reference auto-generated (UUID-based)
      │              status = PENDING

GET /api/bookings/my/  ──►  filtered to request.user  ──►  returns only this user's bookings
```

Still missing, and exactly what Phase 9 builds: nothing here actually takes payment or moves `status` from `PENDING` to `CONFIRMED` yet. Right now a `Booking` existing just means "an attempt was made" — it becomes a real, paid-for ticket only after Razorpay verification.
